Claude Code는 읽기 전용에서 시작한다

Claude Code는 기본적으로 읽기 전용이다 — 파일 편집과 명령 실행은 명시적 승인을 요구하고, 실행된 디렉터리와 하위 폴더에만 접근한다. 이 동작을 네 가지 메커니즘이 통제한다.

4가지 통제
권한 모드 / allow·deny·ask 규칙 / Hooks / 샌드박스
모델 ≠ 통제
프롬프트·CLAUDE.md는 Claude가 "시도하려는 것"을 바꿀 뿐 — 허용 여부는 Claude Code가 강제
점검
/permissions로 활성 규칙과 출처를, /config로 병합된 전체 설정을 확인
실전 예시
# 새 저장소·낯선 코드는 plan 모드로 시작 — 읽기만 하고 변경 없음
permission modes The dial

권한 모드로 개입 강도를 조절한다

다섯 가지 모드가 "얼마나 물어볼지"를 정한다. Shift+Tab으로 세션 중 순환하거나, settings.json의 defaultMode로 고정한다.

default / acceptEdits
안전 기본 / 파일 편집 자동 승인 (활발한 개발용)
plan
읽기·분석만, 변경 불가 — 큰 작업 전 검토
dontAsk / bypass
권한 프롬프트를 전부 거부(사전 승인 도구만) / 모든 도구 자동 승인(YOLO) — deny·훅은 그래도 먼저 평가
실전 예시
"defaultMode": "acceptEdits" — 세션마다 적절한 모드로 시작
allow / deny / ask Declarative rules

allow·deny·ask 규칙으로 도구 접근을 박는다

settings.json의 permissions 객체에 규칙을 선언한다. 모드가 큰 다이얼이라면, 규칙은 개별 도구·명령 단위의 정밀 제어다.

형식
Tool 또는 Tool(specifier) — 글로브 * 지원 (Bash(npm run *))
세 종류
allow(승인 없이 사용) / deny(차단) / ask(매번 확인)
범위 한계
Read·Edit 규칙은 내장 파일 도구와 인식된 Bash 명령(cat·sed 등)에만 — Python·Node 스크립트가 직접 여는 파일엔 안 먹음
실전 예시
deny: ["Bash(rm -rf:*)", "Read(./.env*)"]
eval order Deny always wins

평가 순서를 알아야 함정을 피한다

도구 호출은 Hooks → deny → allow → ask → 모드 순으로 평가된다. 첫 매칭 규칙이 이기고, deny는 bypassPermissions 모드에서도 항상 우선한다.

흔한 함정
deny: Bash(npm *)가 있으면 allow: Bash(npm run test)를 넣어도 차단됨 — deny가 먼저
계층
관리자 > 프로젝트 > 로컬 > 유저 — 프로젝트 설정이 유저 설정을 이긴다
신뢰성 주의
Read/Write deny 규칙은 동작 불안정 이력(공개 이슈) — 보안 핵심 제약은 PreToolUse 훅과 함께 이중으로
실전 예시
# 규칙이 안 먹으면 /permissions 로 어느 규칙에 걸렸는지 확인
/sandbox OS-level isolation

샌드박스로 OS 레벨 방어선을 친다

권한이 "Claude가 무엇을 시도할 수 있나"라면, 샌드박스는 OS 레벨 강제다 — Bash 명령과 그 자식 프로세스의 파일시스템·네트워크 접근을 제한한다. 둘은 상호 보완이다.

적용 범위
Bash 도구 전용 (Read·Edit·WebFetch 등엔 권한 규칙으로)
설치
macOS는 Seatbelt로 기본 동작, Linux·WSL2는 bubblewrap·socat 필요
핵심 가치
프롬프트 인젝션이 Claude의 판단을 뚫어도, 샌드박스 경계는 못 넘는다
실전 예시
/sandbox 활성 + autoAllowBashIfSandboxed — 막아주니 bash 프롬프트 생략
auto vs bypass The autonomy edge

자율성의 양 끝 — auto 모드와 bypass

완전 자율로 가는 길은 둘이다. auto 모드는 분류기가 호출마다 위험을 평가해 안전한 건 승인·위험한 건 차단한다 — --dangerously-skip-permissions보다 안전한 대안.

auto 모드
분류기가 대량 삭제·데이터 유출·악성 코드를 차단; "don't push" 같은 명시적 경계도 존중 (가용 플랜은 확장 중 — 공식 docs 확인)
bypass
--dangerously-skip-permissions는 모든 프롬프트 우회 — 격리된 컨테이너·VM에서만 (Docker --network none)
조직 잠금
disableBypassPermissionsMode로 사용자의 bypass 자체를 차단
실전 예시
# 자율 작업은 auto 모드 우선 — bypass는 격리 환경 한정
