Codex CLI Playbook · 05

권한·보안 심화 안전하게 풀어주기

샌드박스와 승인은 별개의 두 손잡이다 — 모드 이해, 승인 정책, 권한 프로파일, 스마트 승인, Windows 샌드박스, 정책 진단까지 자율성을 안전하게 푸는 6단계.
--sandboxSandbox modes
-a / --ask-for-approvalApproval policy
permission profilesReusable presets
/experimentalSmart Approvals
/sandbox-add-read-dirWindows sandbox
/debug-configAudit the policy
STEP 1—2

두 손잡이 이해

샌드박스 모드(파일·네트워크 경계)와 승인 정책(언제 멈춰 묻나)은 서로 독립된 손잡이다.

STEP 3—4

재사용하고 자동화

권한 프로파일로 정책 묶음을 재사용하고, Smart Approvals로 승인 검토를 리뷰어 에이전트에 맡긴다.

STEP 5—6

플랫폼과 진단

Windows 샌드박스의 읽기 경로를 다루고, /debug-config로 정책이 왜 그렇게 먹는지 추적한다.

--sandbox Sandbox modes

샌드박스 3단계 이해

--sandbox(-s)는 모델이 만든 셸 명령의 파일·네트워크 경계를 정한다. read-only는 전체 파일시스템 읽기만·네트워크 없음, workspace-write는 워크스페이스 안 편집과 일상 명령 허용(로컬 작업 기본값), danger-full-access는 경계 없음 — 컨테이너·VM처럼 이미 격리된 환경에서만 쓴다.

모드read-only / workspace-write / danger-full-access
사용 시점검토는 read-only, 로컬 개발은 workspace-write, 격리 환경만 full-access
주의workspace-write 기본 쓰기 루트는 cwd·/tmp·$TMPDIR, 네트워크는 기본 차단
실전 예시
$ codex -s read-only "코드 구조 분석" $ codex -s workspace-write "버그 수정" # danger-full-access는 격리 환경 전용
-a / --ask-for-approval Approval policy

승인 시점 고르기

-a / --ask-for-approval(config approval_policy)는 Codex가 명령 실행 전 언제 멈춰 물을지를 정한다. untrusted는 항상, on-request는 샌드박스 경계를 넘을 때, never는 묻지 않는다. 샌드박스 모드와는 독립된 손잡이 — 둘을 같이 맞춰야 의도한 자율성이 나온다.

옵션untrusted 항상 / on-request 경계 넘을 때 / never 안 물음
권장로컬 저자동화는 workspace-write + on-request 조합
폐기on-failure deprecated. --full-auto도 deprecated 편의 플래그 — 명시적 플래그 권장
실전 예시
$ codex -a on-request \ -s workspace-write "기능 추가" # --yolo = --dangerously-bypass-... (비권장)
permission profiles Reusable presets

권한 프로파일로 재사용

같은 정책 묶음을 매번 플래그로 치기 싫으면 named 권한 프로파일로 묶는다. config.toml의 [profiles.NAME]에 sandbox_mode·approval_policy 등을 적고 codex -p NAME으로 실행한다. 빌트인 프로파일로 :read-only·:workspace·:danger-no-sandbox가 있다.

위치config.toml의 [profiles.<이름>] 섹션
구성sandbox_mode, approval_policy, writable roots 등을 한 묶음으로
연계codex -p <이름>으로 적용. 빌트인 :read-only·:workspace·:danger-no-sandbox
실전 예시
# config.toml [profiles.safe] sandbox_mode = "read-only" $ codex -p safe "구조만 분석"
/experimental Smart Approvals

스마트 승인 켜기

/experimental로 실험적 기능을 토글한다 — 그중 Smart Approvals는 승인 가능한 요청을 자동 리뷰어 에이전트에 먼저 보내 실행 전 검토하게 한다. config의 approvals_reviewer를 user(수동)에서 auto_review(자동 검토)로 바꾸는 방식. 토글 후 재시작 안내가 뜨면 재시작한다.

진입 방법/experimental → 기능 토글 (Apps·Smart Approvals 등)
효과승인 요청을 자동 리뷰어가 실행 전 검토 — config approvals_reviewer = "auto_review"
주의experimental — 동작·키는 버전에 따라 변할 수 있음. 토글 후 재시작 필요할 수 있음
실전 예시
> /experimental ☑ Smart Approvals # config: approvals_reviewer = "auto_review"
/sandbox-add-read-dir Windows sandbox

Windows 샌드박스 다루기

/sandbox-add-read-dir는 Windows에서 네이티브 실행할 때만 쓰는 명령이다. 절대 경로를 주면 Codex가 Windows 샌드박스 정책을 갱신해, 이후 샌드박스 안 명령이 그 디렉터리를 읽을 수 있게 한다. 현재 읽기 루트 밖의 경로를 읽어야 하는 명령을 풀어주는 용도.

플랫폼Windows 네이티브 실행 전용 (WSL2 아님)
사용 시점읽기 루트 밖 절대 경로를 명령이 읽어야 할 때
주의인자는 실존하는 절대 디렉터리여야 함. 쓰기 확장은 --add-write-dir
실전 예시
> /sandbox-add-read-dir C:\data\refs ▸ Windows 샌드박스 정책 갱신 ▸ 해당 경로 읽기 허용 # 이후 명령에 적용
/debug-config Audit the policy

정책 진단하기

설정이 의도대로 안 먹을 때 /debug-config가 설정 레이어 우선순위(낮은 우선순위부터)와 정책 출처를 찍어 준다. allowed_approval_policies·allowed_sandbox_modes·rules· experimental_network 같은 항목까지 보여 줘, 관리 환경의 requirements.toml 제약이 왜 적용됐는지 추적할 수 있다.

사용 시점config.toml 값과 실제 적용값이 다를 때
확인 항목레이어 우선순위, allowed_* 정책, rules, experimental_network
트러블슈팅관리 환경은 requirements.toml이 never·danger-full-access를 막을 수 있음
실전 예시
> /debug-config layer 우선순위 (낮은 것부터) # 어디서 덮였나 allowed_sandbox_modes: [...]
6단계 아크
샌드박스 모드 → 승인 정책 → 권한 프로파일 → Smart Approvals → Windows 샌드박스 → 정책 진단
권한은 풀수록 빠르지만 위험도 같이 커진다 — 기본값에서 시작해 신뢰하는 저장소에서만 한 칸씩 푼다. 이로써 플레이북 5편 완결.
